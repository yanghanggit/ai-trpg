## 定位

AI TRPG 是一个服务器优先的 RPG 内容引擎：服务端持有唯一世界状态，内容包定义故事，客户端通过 HTTP 契约接入。Web 客户端仍在开发，是参考客户端与验证器；引擎不依赖它。

项目不实现特定规则体系，也不把故事逻辑写进提示词。“纯服务器”指服务端是产品核心，客户端可替换。

## 一、工程结构、技术选型与基建选型

### 1.1 仓库结构

仓库是标准的 pnpm workspace monorepo。服务端内部采用分层模块化单体。

| 位置 | 职责 |
| --- | --- |
| `apps/server` | 服务端：路由、编排、游戏服务、持久化、LLM、检索、图像、作业 |
| `apps/web` | 参考 Web 客户端：页面、交互、mock 目录 |
| `packages/shared` | 跨端稳定事实：服务名、API 版本、默认端口 |
| `packages/api-client` | 契约层：生成的类型、`openapi-fetch` 客户端、错误适配 |
| `apps/server/seeds` | 内置内容包：战役设定、剧本、知识库与检索评测集 |
| `apps/server/test` | 服务端集成测试与架构边界守卫 |
| `docs/` | 引擎知识库，按单一所有者组织 |
| `scripts/` | 仓库级工具：截图、端口检查、mock 隔离检查、清理 |
| `logs/`、`images/` | 运行期产物：轨迹、提示词、记忆、快照、生成资产 |

这套结构的作用是给扩展点定位置。新增动作落在动作调度表，新增内容包落在 `seeds/index.ts`，新增模型或图像供应商落在对应 adapter，新增客户端只消费契约。依赖方向、持久化边界、状态写入点、提示词泛化性与工具命名都有源码扫描测试；越界会在类型检查或测试阶段暴露，而不是等到运行期才发现。

| 扩展动作 | 固定落点 | 守卫 |
| --- | --- | --- |
| 新增角色动作 | `game/actions/registry.ts` 加一行，补解析、解析结果与落账 | 漏写编译失败；结算测试 |
| 新增内容包 | `seeds/index.ts` 显式注册，内容经同一套校验 | `parseContentPack`、内容契约测试 |
| 新增模型 / 图像供应商 | 实现 provider 接口，接在 `llm/` 或 `imagegen/` 下 | 边界测试阻止领域层 import 适配器 |
| 新增 HTTP 端点 | `routes/` 声明 Zod schema，`game-ops/` 补编排 | response schema 进契约；路由测试 |
| 新增客户端 | 只读 OpenAPI 生成类型 | 契约生成与类型检查 |

### 1.2 技术选型

| 层 | 选型 | 作用 |
| --- | --- | --- |
| 语言与工程 | Node.js 22、TypeScript、pnpm workspaces | 全栈同语言、强类型、单一锁文件 |
| API | Fastify、Zod、OpenAPI 3.1、`openapi-fetch` | 路由 schema 是唯一契约源，客户端类型由契约生成 |
| 数据 | PostgreSQL、Drizzle、pgvector | 关系状态与向量检索在同一实例；迁移由 schema 生成 |
| 模型接入 | provider 无关的 `llm` 层、DeepSeek 适配器 | 换模型或接本地网关时不改编排层 |
| 检索 | Transformers.js 本地 embedding、pgvector | 不依赖外部 embedding 服务；模型与精度可配置 |
| 异步 | 自建 PostgreSQL 持久作业队列 | 长耗时 LLM pipeline 不占 HTTP 请求；租约、串行键、重试 |
| 图像 | provider 无关的 `imagegen` 服务与 CLI | 图像生成不进入游戏事务，资产与 meta 成对落盘 |
| 质量 | Vitest、Biome、markdownlint、GitHub Actions | lint、typecheck、test、build 可自动回归 |
| 参考客户端 | React、Vite、TanStack Query | 验证观看者投影与玩家动作路径，不作为引擎依赖 |

### 1.3 结构收益

内容、引擎、契约、客户端各有目录与所有者。生成物不手改，客户端类型从服务端 schema 派生。服务端有 90 个测试文件、600 多个用例；CI 跑 lint、typecheck、test、build。前期接线更多，边界问题更早暴露。

## 二、RPG 引擎设计

### 2.1 四个核心实体

`World`、`Stage`、`Actor`、`Item` 是内容定义；建局时物化为数据库中的运行时状态，之后以数据库为唯一真相。四者对应四个责任面。

| 实体 | 是什么 | 设计目的 | 带来的能力 |
| --- | --- | --- | --- |
| `World` 世界 | 一局故事的世界，约等于一个剧本 | 把跨舞台裁决、世界级记忆与收尾集中到一处 | 故事有统一尺度与终点；局部舞台不能替代世界做收尾 |
| `Stage` 舞台 | 角色活动的地点，有自己的记忆与回合 | 让地点成为持续变化的对象，而不是静态地图 | 环境、锚点、通道可以随剧情与角色行动变化，并由本舞台仲裁 |
| `Actor` 角色 | 唯一行动主体 | 统一 NPC 与玩家控制 | 玩家接管只改变控制者，不改变身份、记忆、装备与规则 |
| `Item` 道具 | 可拿取、穿戴、使用的东西 | 把后果与规则挂到可转移的载体上 | 内容可以声明武器、护具、钥匙、材料的效果，不需要为每个故事写引擎分支 |

四者的配合关系是：世界定义舞台与角色，舞台承载角色、锚点与道具，角色通过动作作用于舞台与道具，道具把动作转化为具体后果。世界做跨舞台裁决，舞台维护本舞台事实，角色提交行动，道具承载规则。

这套拆分让每个问题只有一个归属：故事尺度归世界，地点状态归舞台，行动主体归角色，规则载体归道具。LLM 只做判断与表达，状态变更由引擎完成。

### 2.2 action 是模型与引擎的接口

`action` 是模型提交意图的唯一形式。模型不直接改状态，只提交动作计划；动作是否可用、目标是否合法、后果如何结算，由引擎判断。模型输出因此被限制在结构化意图内，状态写入仍由代码完成。

角色侧目前有 21 个动作，按用途分为：沟通（`say`、`whisper`、`announce`、`call`）、移动与传送（`move`、`teleport`）、隐匿（`hide`、`reveal`）、战斗（`strike`、`cleave`、`brawl`）、物品与交互（`inspect`、`steal`、`loot`、`give`、`pickup`、`use`、`fit`、`equip`、`unequip`）与等待（`wait`）。舞台有 6 个仲裁动作，世界有 2 个裁决动作。这组动作覆盖 RPG 的基本玩法要素：交流、移动、探索、战斗、物品、隐匿与地点变化，当前同时作为动作系统的测试清单。

动作的可用性由声明决定：角色固有动作、技艺授予的动作、穿戴武器借出的攻击动作、持有道具借出的使用动作。新增动作在统一动作表中登记，并补齐解析、结算与测试。

优势是：内容决定角色能做什么，引擎决定做了之后发生什么；模型只提出计划，不能绕过动作清单，也不能凭空创造效果。

### 2.3 机制层

`Skill`、`Affix`、`StatusEffect` 围绕 action 与结算展开，分别承载能力组织、道具后果与角色属性修正。它们不是新实体，而是内容声明进入引擎结算的三种入口。

| 机制 | 宿主 | 引擎中的作用 | 对玩法的支撑 |
| --- | --- | --- | --- |
| `Skill` 技艺 | 内容层，角色定义 | 把多个固有动作组织成一项能力 | 内容可以按职业、训练或天赋组织动作，不需要引擎新增技能实体 |
| `Affix` 词缀 | 道具，按动作触发 | 把 `strike` / `cleave` / `use` / `fit` 的后果挂到道具上 | 装备改变可用战术；后果随道具转移、掉落与搜刮 |
| `StatusEffect` 状态效果 | 角色 | 把属性修正挂到角色，由动作结算读取 | 角色的状态可以影响数值与策略，而不必写进每个动作 |
| `Stats` 属性 | 角色、道具、状态效果共用 | 统一数值形状，区分源属性与终值，结算时生成快照 | 面板、结算与存储读同一份数字，策略判断有稳定依据 |

引擎在结算上分两层：确定性计算与推理追加。确定性层处理数值、属性、伤害、生命等可复现部分；推理层处理文本条件、泛化判断与增量后果。顺序是先计算、后推理，推理只追加、不回滚。

这种分工让传统规则与 LLM 泛化同时成立：玩家可以依据明确数值、装备与状态做策略；模型可以处理规则没有枚举的现场情况；两者都收束在 action 与结算上，不会扩散成自由叙事。目标仍由世界、舞台与角色内容定义，机制层负责把行动转成可结算的后果。

### 2.4 回合与 agent 拓扑

| 类别 | 组成 | 作用 |
| --- | --- | --- |
| 记忆实体 | 世界、舞台、角色各自的回合 | 持有个体记忆，按实体逐个推进 |
| 世界职能 | 词缀、故事整理、记忆压缩、玩家对话审核 | 世界级单例，不持有实体记忆；一次推理或一次改写 |
| 旁路 | 外观、死亡掉落、只读探针 | 借目标记忆做一次推理，不新建实体 |

### 2.5 内容包与题材包络

框架层不含具体故事。故事通过内容包 `{ world, knowledge }` 进入；内置 `seeds/` 与外部 JSON 走同一契约。建局时显式指定内容，先校验再物化为游戏状态；之后改内容不会回改已有游戏。

题材包络定义引擎支持的 RPG 基础：角色有身体与数值，道具可持有、穿戴和转移，世界由相互连接的舞台组成，战斗可以致死并留下尸体与遗物，角色只知道他观察到的事，超自然能力由内容决定是否启用。包络内的玩法通过声明与机制扩展；包络外需要新的领域设计。

这样新故事主要增加内容与知识库，不增加引擎分支。

## 三、数据与状态：数据库作为唯一真相

游戏状态、事件、记忆、检索与作业都存 PostgreSQL。回合从库里读、在短事务里写；进程重启不丢状态，服务端不保留跨请求的权威世界对象。同一局写入由行锁串行化，版本号只记录变更；状态不做跨请求缓存。并发写入因此有确定顺序，重启、回放与排查都以同一份数据为准。

| 选择 | 目的与好处 |
| --- | --- |
| 状态全在数据库 | 重启可恢复；并发写入有序；回放、审计与 CLI/HTTP 读取同源 |
| 单个 PostgreSQL | 一套备份、账号、迁移与权限；关系状态与 pgvector 检索同库；不需要双写 |

关系库存对局、舞台、角色、道具、事件、记忆、作业与审核；向量表只存世界知识，按内容版本与模型隔离，带访问标签。向量是派生索引，可重建；游戏状态是权威，不能从向量恢复。一个实例让内容版本、向量与访问标签在同一库内核对，访问控制读同一份角色状态。代价是向量检索与游戏写入共享资源，知识规模变大时再评估独立检索。

## 四、记忆管理

### 4.1 记忆与状态分开

| 数据 | 内容 | 用途 |
| --- | --- | --- |
| 活状态 | 当前环境、位置、背包、生命 | 回合读取与结算 |
| 记忆 | 主体经历过的事件与开局基线 | 该主体后续推理 |
| 公共事件流 | 上帝视角的事件 | 客户端展示、审计、故事整理 |
| 世界知识 | 世界层面的固定事实 | 角色按知识标签检索 |

状态每回合现拉，记忆只记录历史与基线。这样长局不依赖上下文窗口，角色也不会把公共事件或世界知识当成自己的经历。

### 4.2 三个记忆主体

世界、舞台、角色各自持有独立记忆。记忆只由引擎写入，记录开局信息、行动事实与观察；任务提示词与工具轨迹不写入记忆。记忆超长时压缩为摘要，旧消息保留归档。

好处是长局一致、上下文成本可控，角色视角不会被其他人的记忆污染。

### 4.3 信息边界与检查

名字是观察者的认知，同一角色在不同观察者眼里可以有不同称呼。角色只读自己的记忆、当前舞台的可见事实与按知识标签过滤的世界知识；舞台与世界掌握更大范围，但不会把全知内容下推给角色。

记忆导出、探针、轨迹、提示词导出、名字审计与快照提供回放和排查入口。信息边界支撑悬疑、伪装、侦探等玩法，也让“角色为什么这么行动”可以回到当时的记忆与观察。

## 五、LLM 与图像服务接入

### 5.1 LLM

服务端 LLM 分两层：`llm` 提供 provider 无关的协议、批量与 agent loop；`deepseek` 是默认 DeepSeek 适配器，依赖方向固定为 `deepseek → llm`。换模型或接本地网关只替换适配器，不改游戏编排。

LLM 是服务端内部依赖，浏览器不接触模型名、提示词、工具或密钥。模型输出是不可信中间数据：计算端先提交数值、伤害与生命，推理端再追加词缀、外观与死亡掉落；推理失败只丢增量，不回滚已提交结果，也不进入数据库事务。

### 5.2 图像

`imagegen` 提供 provider 无关的图像生成服务、批量编排与资产落盘，厂商适配器放在 `imagegen/providers/`。图像生成是内容工具，不进入游戏事务；调用方拿到已落盘的资产与 meta，而不是远端 URL。当前入口是 CLI，资产尚未绑定世界或舞台。

### 5.3 异步

长耗时 LLM pipeline 由 PostgreSQL 持久作业队列承载：入口入队返回 `jobId`，worker 在 HTTP 请求之外执行，重启不丢，同一世界或房间的 pipeline 不并发。HTTP 入队 / 查询 / SSE 尚未接入。

## 六、开发工作流：agent:game 与 agent:api

### 6.1 coding agent 的自运转边界

项目按“coding agent 可自运转”配置开发流程：agent 读代码与文档，用 CLI 建局、推进、复现，读状态、记忆、探针、轨迹与快照，修改代码或提示词，再跑测试与评测。它形成“修改 → 运行 → 观测 → 回归”的闭环。

可自运转的是工程闭环，不是产品决策。玩法平衡、叙事质量、设定一致性、安全尺度与上线判断仍由人负责。提示词调整属于行为变更：结构性测试守住契约、工具名与泛化性，叙事质量需要基线局、轨迹对比和人工抽检。现有 CLI、轨迹、探针、记忆导出、快照与评测支撑这个闭环；自动提示词回归集、预算/沙箱与人工闸门仍需补齐。

### 6.2 两个入口

两者使用同一组子命令、参数与输出信封，agent 可以脚本化建局、推进、读取与排查，不依赖 Web。

| 入口 | 路径 | 用途 |
| --- | --- | --- |
| `agent:game` | 直连 PostgreSQL，按实体显式推进 | 引擎调试、内容验收、回合级排查 |
| `agent:api` | 走运行中的服务端 HTTP | 接口走查、契约验证、跨进程回归 |

`agent:game` 可以用 `player-*` 以某个角色身份直接提交单个动作，绕过计划和模型，适合确定性复现。`agent:api` 一次调用一次请求，不缓存状态，验证的是 HTTP 契约和业务编排。

### 6.3 共用编排

两条入口共用 `game-ops/` 编排，玩法规则、动作解析与落账只有一份实现；`agent:api` 只多一层 HTTP 契约。同一命令在本地与 HTTP 下对应同一端点与同一份编排，行为不会分叉。

### 6.4 典型流程

内容编写 → 建局 → 逐个实体推进 → 读投影 / 探针 / 记忆 → 看轨迹与快照 → 修正。自动化测试用 `app.inject()`，不监听真实端口。

### 6.5 工具边界

两个 CLI 是开发工具，不是产品 API。开发期身份是 `Bearer <username>` 占位，对外接入前替换为正式鉴权。

## 七、现状与目标

### 7.1 当前测试剧本与已验证功能

已验证功能包括：从 seed 或外部 world 建局、玩家接管、21 个角色动作、NPC / 舞台 / 世界回合、外观与死亡掉落、RAG 查询、记忆压缩、快照、故事整理、探针、作业冒烟与图像 CLI。测试剧本覆盖探索、战斗、偷窃、搜刮、密室开门与多结局。

### 7.2 引擎目标

- 内容可替换：新增或替换内容包，不需要写故事特判，也不需要改引擎。
- 信息有边界：角色只知道自己观察到的事实，全知信息不下推给角色。
- 客户端可替换：新客户端只依赖 OpenAPI 契约，不 import 引擎，不读内部状态。

## 八、类型实验

以当前 RPG 为基线，另做两个思想实验：陪伴型乙女游戏与直播型游戏。判断方式是看现有组件如何表达玩法。

### 8.1 基线：当前 RPG

当前 RPG 的核心是身份不对称、属性对抗、多角色互动与信息不对称。

| 玩法要素 | 现有表达 |
| --- | --- |
| 多角色互动 | 角色与舞台，加上沟通动作与同舞台行动 |
| 协作 | `give` / `use` / `fit` / `equip`，舞台锚点与共享舞台 |
| 对抗 | `strike` / `cleave` / `brawl`，`Stats`、`Affix`、`StatusEffect`、生命与死亡 |
| 信息不对称 | 角色私有记忆、观察者相对名字、隐匿、`inspect` / `steal`，世界知识按标签过滤 |
| 多舞台 | 有向舞台图、`move` / `teleport`、舞台自己的环境与记忆 |

这些要素是引擎原生能力，不依赖故事特判。

### 8.2 思想实验一：陪伴型乙女游戏

形态是单主角、多个关系角色、多个舞台场景。世界承载故事线与收尾，舞台承载约会、日常与事件场景，角色承载主角与关系角色。`say` / `whisper` / `give` / `use` / `inspect` / `move` 覆盖对话、赠礼、查看与场景移动；每个角色独立记忆记录共同经历与称呼，记忆压缩支持长线；外观与装备表达换装，图像生成用于立绘或 CG。舞台回合更新场景，世界职能整理故事与审核玩家台词。

### 8.3 思想实验二：直播型游戏

互动直播：主播扮演主角，观众通过弹幕、投票或礼物影响行动。观众不作为角色；观众输入聚合成有限动作或舞台/世界指令，动作校验保证只落在合法动作上。世界、舞台、角色承载主播、NPC 与场景；观看者投影给主播界面，公共事件流按可见性过滤给直播叠加层，控制面状态给导演。玩家对话审核处理观众文本，过程轨迹与快照用于回放与恢复；礼物映射为道具、舞台事件或世界指令；长耗时生成走作业队列，图像生成产出叠加层或场景图。

三类玩法复用同一组核心组件，类型差异由内容、输入方式与表现层决定。
