# LLM 基础组件

## 分层

服务端 LLM 分两层：`llm` 是与 provider 无关的类型、协议、批量与 agent loop；`deepseek` 是 DeepSeek 的 HTTP 实现与默认绑定。依赖方向固定为 `deepseek → llm`，`llm` 不得 import 具体 provider，因此接本地模型或其它兼容网关时，编排层不需要改。内部字段 camelCase，snake_case 只出现在 provider 的 wire 边界。

→ 参见：[架构与契约](architecture.md)、[Agent 与工具](agents.md)

## 循环与批量

循环只依赖 `ChatCompletionService`，工具定义与 handler 由调用方注入；终止工具、纠偏重试与历史边界属于编排层。循环不判断工具能否并发——由 LLM 决定一次返回多个 `tool_calls` 还是分多轮对话，循环按返回顺序串行执行，保证状态变更顺序确定。

批量有并发上限，结果与请求等长同序，意外异常也收敛为结果里的 error。请求与结果是值对象，service 无状态，同一个客户端可并发复用。

请求与响应的原文只进过程轨迹，本层不另设并行留痕。

→ 参见：[开发期 Agent 工作流](debug-workflow.md)

## 错误与重试

失败分两类：预期内失败走结果而不抛异常（超时、连接错误、非 200），真正的程序错误与取消仍然抛出。`ChatError` 的 retryable 只是元数据，通讯层不自动重试：408 / 429 / 5xx 可重试，400 / 401 / 402 / 422 通常是请求、鉴权或余额问题。重试策略由业务层决定，避免无条件重放带副作用的请求。

编排层的重试分成两套，互不重叠：通讯重试只对可重试失败生效，就地重发同一请求，不占工具轮次；纠偏重试只处理模型未调用终止工具就结束的情况。业务按回合强度开启通讯重试，基础设施不替业务猜。

重试用尽或错误不可重试时，循环仍按原语义进入下一轮；整轮仍未成功则返回失败，由业务决定是否落账或重跑回合。单次请求的超时也由业务透传。
