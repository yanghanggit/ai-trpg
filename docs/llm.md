# LLM 基础组件

## 分层

服务端 LLM 分两层：`llm` 是与 provider 无关的类型、协议、批量与 agent loop；`deepseek` 是 DeepSeek 的 HTTP 实现与默认绑定。依赖方向固定为 `deepseek → llm`，`llm` 不得 import 具体 provider，因此接本地模型或其它兼容网关时，编排层不需要改。这一层不对外暴露。

→ 参见：[架构与契约](architecture.md)

## 核心设计

- 请求与结果是值对象，service 无状态：同一个客户端可并发复用，不在实例上残留上一轮响应。
- 预期内失败走结果：超时、连接错误、非 200 填进结果的 error 字段而不抛异常；真正的程序错误与取消仍然抛出。
- 批量有并发上限：同时在飞的请求数由信号量限制，结果与请求等长同序，意外异常也收敛为 error。
- agent loop 与 provider 解耦：循环只依赖 `ChatCompletionService`，工具定义与 handler 由调用方注入；终止工具、纠偏重试与历史边界属于编排层。循环不判断工具能否并发——由 LLM 决定一次返回多个 `tool_calls` 还是分多轮对话，循环按返回顺序串行执行，保证状态变更顺序确定。
- 内部字段 camelCase，snake_case 只存在于 provider 的 wire 边界，避免命名扩散到业务层。

## Prompt 分层

system prompt 是**宪法与索引**：实体身份、世界设定、全局规则。它进入长期 memory、不参与 compact，因此只写稳定且必须永远成立的内容，不写执行细节，也不写本轮任务。

执行细节向后推：**任务提示词**（每轮 input）给本轮可见事实、当前状态与目标；**工具描述**给动作的规则与约束——工具随每次请求下发，等于变相的任务提示词，所以「怎么提交 environment」这类细则写在工具描述里。

判断标准：内容一变再变、只对某类动作生效、或者只对本轮生效，就不该进 system prompt。

## 运行时 agent 的世界设定

`campaignSetting` 是每局的世界宪法。凡是会推理并产出世界面文本、或会改写长期记忆的运行时 agent，都要拿到它：否则材质名、可见后果与压缩后的术语会退回模型的世界外常识，而下游只会拦系统引用与角色名，看不出题材越界。

设定是约束，不是剧情事实。带 memory 的 actor / stage / world 与复用其 memory 的外观、探针由 system prompt 携带；无 memory 或自建 system 的掉落、词缀、故事整理与记忆压缩把它作为任务上下文注入。玩家对话审核沿用同一分层：设定是任务数据，system 只放平台规则。唯一例外是开发期的框架文本审查，它必须不带世界内容，否则无法判断框架是否依赖具体题材。

→ 参见：[数据驱动](data-driven.md)、[玩家对话审核](dialogue-audit.md)

## 请求与响应记录

每次请求与响应的原文（生成参数、工具定义、上下文消息、推理与工具调用）由过程轨迹记录，本层不再单独落盘。不另设并行留痕：同一份 prompt 写两处，只会让复盘多一次跨库对齐。

→ 参见：[开发期 Agent 工作流](debug-workflow.md)

## 错误与重试

`ChatError` 的 retryable 只是元数据，通讯层不自动重试：超时、连接错误与 HTTP 408 / 429 / 5xx 可重试，400 / 401 / 402 / 422 通常是请求、鉴权或余额问题。重试策略由业务层决定，避免在通讯层无条件重放带副作用的请求。

编排层的重试分成两套，互不重叠：通讯重试只对可重试失败生效，就地重发同一请求，不占工具轮次；纠偏重试只处理模型未调用终止工具就结束的情况。业务按回合强度开启通讯重试，基础设施不替业务猜。

重试用尽或错误不可重试时，循环仍按原语义进入下一轮；整轮仍未成功则返回失败，由业务决定是否落账或重跑回合。单次请求的超时也由业务透传。
