# Seed 内容编写原则

内容只回答四件事：世界是什么、谁在哪里、谁能做什么、什么算公开事实。机制、格式、路由与判定归引擎。

写内容前先做一次归属判断，再落笔；判断错了，后面每一层都会漏。

## 所有者

本页拥有跨剧本通用的编写原则，任何 seed 都适用。具体剧本的剧情意图、验收口径与删除条件写在内容目录的随附 md 里；框架与内容的边界、内容入口归数据驱动文档；名字的四个层次归术语表。

→ 参见：[数据驱动目标](data-driven.md)、[术语表](glossary.md)、[公共知识检索](rag.md)

## 六个文件各管什么

| 文件 | 只放 | 不放 |
| --- | --- | --- |
| 战役文件 | 跨剧本不变的世界观与全局规则 | 任何剧本专名、具体机制细节 |
| 剧本文件 | 这一局的世界设定、场景图、角色、物品、开局已知关系与能力清单 | 战役级文本、可随剧本变化的知识 |
| 知识库 | 陌生人可观察、可询问或见于公开记载的固定事实 | 角色名、秘密、当前状态、可移动物品 |
| 评测集 | 与知识库一一对应的检索用例 | 与剧情状态耦合的问题 |
| 注册表 | 内容名到内容包、到剧本的显式映射 | 隐式默认值 |
| 随附 md | 本剧本的意图、验收与删除条件 | 引擎规则、其他剧本的设定 |

## 落笔前的四个判断

1. **机制还是事实。** 伤害怎么算、谁能开哪扇门、允许多少动作，属于引擎与工具说明；世界里发生过什么、谁相信什么，属于内容。
2. **跨剧本还是本剧本。** 换一个故事仍然成立的世界观写进战役；随故事变化的部分写进剧本。
3. **谁会知道。** 公开知识、角色私有信息与当前状态是三件事，分别落知识库、角色设定与场景快照。混一层就会泄漏。
4. **会不会被当成已知。** 名字、秘密、系统路由一旦写进 agent 会读到的位置，就等于直接告诉它；不知道的东西只能来自世界内的告知。

## 命名与引用

- 实体使用层级规范名（`类别.实体`）：角色、场景、物品共用同一套语法，不自创前缀。
- 物品的类型前缀必须与它的大类一致：去掉前缀后的写法是角色实际看到的物品名，前缀只服务归类与路由。
- 跨引用优先用稳定 key：场景连接、角色归属、开局称呼边都用 key，不用展示名。装备槽是唯一按物品规范名引用的地方，因为同一持有者内名字唯一。
- 本名不是称呼：角色设定里可以出现该角色自己知道的名字；其他实体默认不知道，除非内容声明了开局关系，或游戏过程中被告知。
- 描述性称号（父王、守钟的、掘墓人）是身份，不是本名；可以出现在叙述里，也可以作为称呼写入关系边。

→ 参见：[术语表](glossary.md)

## 每一层写什么

### 世界

世界设定回答“这是什么地方、什么算收束、尺度到哪里为止”。收束条件必须写在这里，因为只有世界能结束游戏；场景只能报告，不能收尾。世界能力要显式声明，不依赖引擎默认。

### 场景

场景设定写它是什么、曾经发生什么、为什么重要，以及角色能从这里学到什么。环境写当前快照：此刻可观察的物体、表面、光线、气味与氛围，不含历史、因果、角色名与角色行动，并且必须与场景物品一致。

场景能力逐项声明：每个场景都能刷新环境；只有真的有机关的地方才给开通道的能力；只有跨场景后果的源头才给向世界报告的能力。场景图是有向的：单向用“没有反向边”表达，封闭用“边存在但当前不可通行”表达，不要指望对称推导。

### 角色

角色设定是它自己的全部：历史、性格、说话方式、手段、关系、禁忌与秘密。秘密放这里，不放知识库；触发条件是软约束，由角色自己判断，不写成状态机。

开局简报写进入这一局时的处境、意图与约束，不是单轮任务，也不写工具名。它允许“睡着了”“还没决定”这类状态，但这些是意图，不是保证。

基础体型是稳定身份，只有它进系统提示词；可见外观是当前形象的展示值，种子里的外观是预制快照。穿戴索引与物品列表必须按规范名对得上，否则换装与观察会脱节。

能力逐角色声明。活物会说话、走动、等待；动物不操作物品；不是所有角色都该会攻击或偷窃。语言与发声规则属于该角色，不属于全局规则。

### 公共知识

一条知识要能通过三问：刚进入此地的陌生人能否通过观察、询问或公开记载知道它；角色离开或现场被改变后它是否仍然成立；它是否只是场景描写或当前状态。任一答案为否，就不入库。

知识写成短事实，一条一句，按稳定分类归档。它不承载角色秘密、物品位置、弱点与行为规则。

### 评测

每条知识至少有一个正例覆盖，正例的期望文本必须是该条目的唯一片段；没有的事实用负例守住。评测与知识库同目录维护，改文案时一起改。

## 保密、伏笔与“世界内已知”

秘密只存在于角色设定与私有记忆。知识库是公开的；场景环境只写此刻看得见的东西。伏笔可以露在环境里，但关键事实不能提前交出——看见符文不等于知道暗语。

开局称呼边只声明世界内已经成立的关系；其余名字必须靠自我介绍、他人介绍或可见记载获得。不要用“所有人都知道”这种叙述去要求引擎替你兜底：要么声明一条边，要么保持未知。

## 触发器与结局

暗语、沉睡、忠诚这类软触发写在角色设定或开局简报里，是意图而不是保证；不要为它们写确定性断言，但要保证前置条件可达：钥匙拿得到、门开得了、路走得通、报告发得出。

物品效果是声明式的，故事特有的判断写在词缀或描述里，不为单个故事新增引擎分支。任何不可逆的结果都要有来源与报告者：谁造成了它，谁有权收尾。

## 版本与验收

内容版本与知识库集合绑定：改内容就要升版本并重新入库；开发期直接重置重刷，不做数据搬运。

验收不只看单元测试，还要把内容当一局游戏推演一遍：预定的路径是否真的可达，角色是否真的能从内容里学到该学的东西，公开知识是否经得起“陌生人三问”。护栏由内容测试、框架专名守卫、系统提示词工具名守卫与检索评测共同承担，细节以它们为准。

→ 参见：[开发期 Agent 工作流](debug-workflow.md)

## 反模式

- 把机制、格式或工具名写进战役文本。
- 把场景描写、当前状态或角色秘密写进知识库。
- 用展示名当跨引用键，或给物品配一个与类别不符的前缀。
- 让场景替世界收尾，或让角色替场景决定环境。
- 声明了能力却没有对应的内容路径，或写了路径却没有声明能力。
- 依赖引擎默认行为：不声明动作、不声明能力、指望对称边自动成立。
- 为软触发写确定性断言，或为了测试去硬编码剧情结果。

## 参考实现

当前黑暗奇幻 seed 演示了这些原则：先写明收束条件、三类边（双向、单向、初始封闭）、按角色声明的能力清单、声明式词缀、开局称呼边，以及“伏笔可见但关键事实不可见”的保密分层。它的具体意图与验收见随附 md。
