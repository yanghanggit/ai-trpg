# 开发期 Agent 工作流

两套互补入口，只服务开发、走查与 agent 实验，不是产品 API：`agent:game` 直连 PostgreSQL，按实体显式推进；`agent:api` 逐步请求运行中的业务服务端。两者都复用同一套业务服务层，CLI 只做参数解析、状态读取与结果输出。

## 数据库驱动

子命令与参数以 `pnpm agent:game --help` 为准。要记住的是它的形状：建局必须显式给内容来源，推进必须逐个实体指定，读操作不调用 LLM 也不改状态；玩家接管后可用 `player-*` 以该 actor 身份直接提交单个动作，绕过计划与模型。

对调用方的契约就三条：stdout 只出 JSON（帮助、版本与 `--text` 模式除外），进程日志与用法错误走 stderr，退出码区分成功、运行失败与用法错误。

## 显式推进边界

`agent:game` 不自动编排回合：`stage` 与 `world` 必须显式执行，`create` 必须显式提供内容，RAG ingest、compact 与旧局结构升级都不会自动发生。只有 world 能主动结束游戏；主角死亡只写一条 world 通知，收尾仍然要显式跑 `world`。

## 运行时 system prompt 导出

建局成功后，服务层把本局实际使用的 system prompt 写到 `logs/prompts/`：world 与各 actor/stage 各一份，文件名取实体名、容器目录名带时间戳与内容版本，内容与记忆里的第一条逐字一致。导出是旁路：失败只告警，数据库仍是唯一权威状态。

## 过程轨迹

轨迹是写进 `logs/` 的按局、按天追加事件流：回合边界、LLM 请求与响应、计划与落账、被拒原因、子阶段结果、观察收件人。字段以 `trace schema` 为准，子命令以 `agent:game --help` 为准，两者都不在这里复述。

它刻意做成文件语料而不是日志流：读者顺序是 agent 优先、人其次，要求跑完之后能重新读取、用文本工具统计拒绝与失败、跨局跨天对比同一改动前后的行为；数据库会被重置，轨迹不会——这是它不为分析建表的原因。

观察也进轨迹：谁收到了哪条观察、或者谁都没收到，都是可归因的事实。子阶段结果分 `ok`、`skipped`、`failed` 三态并带原因，`ok` 只代表确实落了账。增量阶段的统一入口只负责失败收敛与轨迹记录，不承载预算、重试或事务策略。

保留以归档为先：压缩之后读取侧照常可读，只有显式删除才真的丢数据。同一份轨迹可按需渲染成人读视图，审阅不必另存一份数据；原文放在围栏里，避免内部标题破坏外层 Markdown。写盘失败只告警，不影响游戏。

进程日志只留启动、失败与降级告警，不承担过程叙事；轨迹回答“为什么”，日志只回答“进程是否健康”，两层不能互相替代。

→ 参见：[LLM 基础组件](llm.md)

## 记忆导出

`agent:game memory` 是只读旁路：把某个 agent 当前的 memory 原样写成 Markdown，不注入当前场景、observation、工具定义与本轮提示词，也不写库、不调 LLM。它与探针同源，区别只在读者——探针让 agent 自己回答，导出把上下文摊开给人。

导出物与轨迹同归 `logs/`，按局归档；文件名编码导出时间、游戏版本与 owner，使文件可排序、可与快照和轨迹对齐到同一状态，并让读者不打开文件就知道是谁的记忆。正文先索引后原文，供先定位再细读。owner 解析只有一处，新增携带记忆的实体时不必改各调试入口。

→ 参见：[Agent 探针](probe.md)、[Actor 记忆](actor-actions-memory.md)

## 文件快照

快照是提交后的只读投影，按 user/game/snapshot 归档，含世界状态与事件；数据库快照额外导出各 agent 的私有 memory。它不是写入源，分支与回溯由数据库层负责。入口只有 `agent:game snapshot`：按目录手工建、列、看快照的命令已随数据库快照落地删除，不再维护第二条快照路径。

## HTTP 走查

`agent:api` 是一次性进程：一次调用发一次 HTTP 请求，不缓存世界状态；stdout 只出 JSON，日志与错误走 stderr，非 2xx 以非零退出码结束。它用于探索与边界试探，不替代 `app.inject()` 回归测试。
