# 行动顺位

行动顺位是「此刻谁先行动」的**快照**：开一条时把全世界还能行动的 actor 按敏捷现值排成一条次序，之后每推进某个 actor 的回合，就给他在这条顺位上的回合计数加一。

它是时间轴上的一环：局之下的推进按顺位走，顺位走完一遍是行动轮，轮里每个角色各有一个回合（词义归[引擎概念用词](terminology.md)）。

行动顺位不推动任何回合：推谁、推几次、什么时候收工，都由调用方决定；没有进行中的顺位时推进照旧，只是不记数。

## 快照

排序在开顺位那一刻一次性算完，落库的是当时的敏捷现值（本体 + 穿戴 + 状态效果，与面板、察觉同一份口径）与名次；之后换装、加状态都不回写。死者不进入顺位：他这一回合已经不能行动，进来只会留下一条永远不动的计数。

名次不分玩家与 NPC：主角、被接管的角色、以及由引擎跑循环的 NPC，都是这条序列上的一个回合。生死与「这一回合谁执行」不落库，是读出时补的两个当下事实——名次是快照，接管与死亡会变。

并列按实体序号升序兜底，不按名字——名字会变，同值必须可复现。排序口径与它的开关归玩法数值层，顺位只消费「已经排好的先后」。

名次从 1 起、同一条顺位内连续，是这条顺位自己的位置，与世界内的实体序号无关。

## 计数与生命周期

计数发生在**回合**上，不是动作上：判据是「这个回合发生过」——有行动落账算，调用方明示的空回合也算（`turns/pass`：跳过失败的一轮、或玩家席位这一趟没动手）。被拒的计划不留下行动事实，所以它要么重试、要么补一个空回合，补不补由客户端决定。

计数发生在回合级的入口上，两条路径各一个：点名推进（`turns/npc`，一个 actor 一个作业）算一个回合，玩家的 `actors/:actor/actions` 一次提交也算一个回合。所以玩家直接提交动作、不跑任何模型，同样在名次上 +1。一个回合只结算一个动作，两路同一口径；想连着做几件事就是几个回合，顺位上各记一次，客户端不需要替它另算。

两条入口都先入队再执行，所以**入队不等于回合发生过**：计数只在落账成功的那一刻记。客户端读顺位看的是计数，不是自己发过几次请求。

开顺位之后才加入世界的 actor 不在名单里，推进他只会静默跳过——快照不追认新人；开顺位之后死掉的人留在名次上，计数保留，只是不再被选中。

一局同时最多只有一条进行中的顺位，这是存储层的硬约束，不是调用约定。完成给它打上标记与完成时间，之后不再记数；移除直接删行，条目随外键级联。完成是收敛：重复完成回同一行，客户端重试「收工」不该看到一次失败；移除相反，删过的 id 再删就是不存在。

## 客户端驱动

顺位把两件事分给两端：服务器持有数据，客户端持有执行权。服务器不代选目标，也不在推进之间插自己的调度——它只回答「这条顺位上谁快轮到」，并在推进发生时记录。于是客户端能自由决定粒度与时机，而两边始终读的是同一份数据。

「谁快轮到」有唯一定义，归服务器：**回合计数最少者，同值取名次靠前**，候选是顺位上还活着的人。读取顺位时这个角色一并给出，还带着它的 `control`，客户端照用即可，不必再实现一遍定义。

执行方由客户端据此分派：`control: "player"` 的那一回合等人拿主意，由客户端直接提交动作；`control: "agent"` 的那一回合交给引擎跑循环。两者都是名次上的标准回合，都计数；接管与放手只改 `control`，不动名次。

人不动手时，客户端替这一席位记一个空回合：计数照加，人会往队尾沉一次，别人不必等他。记的是「轮到过他、他没动」这条事实，不是替谁编动作。不记的代价是他在队首反复被尝试；记了，一轮才能闭合。

顺位还逐条给出 `alive`，所以「走完一遍」也不必猜：活着的条目计数齐平就是一遍，不需要靠「名次回退」这类启发式。但齐平只是读出来的一刻，不是服务器维护的屏障——没有轮次表，也没有「本轮结束」这种状态。

何时收工也由客户端判定：它读得到全表计数，推到什么程度算完是它的判断。一局之内可以有很多条顺位，客户端收工后自行删旧开新。

服务器只拒两件事，都不针对先后本身。一是**视图过期**：四条跑回合的入口（NPC、玩家动作、舞台、world）都带着客户端读到的世界版本，在**执行开始时**比对，版本已经变了就判这次回合失败——这不是权限，而是「别拿旧视图做决定」。比对不在入队时：作业可能排队，入队那一刻的版本证明不了执行时还成立。二是**同一局并发推进**：同一局同时只允许一个回合在跑，后来的入队直接拒，因为模型调用在写事务之外，两发都会跑完整个回合，白烧一次调用还多记一次数。互斥记在库里，所以分进程部署也成立；空回合不占位，它只加一，不跑循环。

承诺的粒度只有单次推进：并发去重认「同一局同时两发」，不认「同一个编排周期」；一次编排周期也没有事务——中途失败时前面已落账的留在库里，续跑靠读数与轨迹。互斥在库里而不是进程内存，所以 API 与 worker 分进程、或多个 worker 并行时仍然成立。两个周期重叠会各自跑出 stage 与 world 回合，服务器不认为那是错：反复推进 stage、world 本身合法，次数与次序都归客户端。玩家空位同理不阻塞——服务器没有「等待玩家」的状态，玩家不动时顺位就停在他身上，是等他、替他待机、还是先推别人，都是客户端的判断。

「推了不该推的人」不拒，只记录：两条跑回合的入口都在过程轨迹里留一条事实，写清这一回合算出的期望名次、实际推的名次、以及是否一致。空回合不记——它只加一，没有「该轮到谁」的判断可对。记录只陈述、不判罚——判据没定之前，轨迹是用来攒证据的。

一条边界：计数只在这条顺位之内，删掉即清零，「这个人总共行动过多少次」不由顺位回答。
