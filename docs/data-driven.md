# 数据驱动目标与当前隔离缺口

> 目标状态：故事是输入，框架是引擎。当前实现已经接近这个形态，但还不是完全隔离。

## 结论

`World`、`Stage`、`Actor`、`Item` 是系统框架概念；故事文本、角色关系、场景图、物品和通关条件应当由内容输入提供，而不是写进 `game` 服务。

当前核心服务大体遵守这个边界：数据库 schema 不含具体故事字段，`createGame` 接受任意 `World`，测试使用独立的 `TEST_WORLD` 也能运行。但仍有几处内容泄漏，集中在一个临时剧本的规则和 CLI 默认入口。

数据驱动是下一步开发目标，不是当前已完成状态。

## 当前隔离边界

| 层 | 状态 | 说明 |
| --- | --- | --- |
| 数据库 schema | 已隔离 | 表结构只表达 world / stage / actor / item / message / memory 等通用概念 |
| 领域类型 | 基本隔离 | `World` / `Stage` / `Actor` / `Item` / `Weapon` 均为通用容器 |
| 故事内容 | 已隔离到 seed | 场景名、角色 profile、对白线索、连接、物品、每个角色的 `actions` 能力清单和初始状态位于 `seeds/dark-fantasy.ts` |
| NPC prompt | 内容驱动 | 世界设定、角色 profile、场景环境从输入与数据库读取 |
| 行动应用层 | 有泄漏 | 通关条件直接引用当前剧本的 stage 名与钥匙名 |
| 状态层 | 已隔离 | 状态只作容器；沉睡与苏醒由 profile / LLM 判断，不写系统规则 |
| CLI 创建入口 | 有泄漏 | 默认导入当前演示剧本，不能直接选择另一份内容 |
| 测试 | 已隔离 | `TEST_WORLD` 与演示剧本独立 |

## 未隔离的具体部分

### 1. 钥匙通关条件

`game/actions/use.ts` 中定义了当前故事的：

- `SEALED_GATE_STAGE_NAME`
- `SEALED_GATE_KEY_NAME`

`actions/use.ts` 用这两个常量判断 `use` 是否结束游戏，并在反馈中写死“封骨之门打开了”。

问题不在“使用道具通关”这个能力，而在框架层知道了当前故事的具体场景名和物品名。

未来应把完成条件作为内容数据：

- stage 级完成条件；
- 触发动作类型；
- 必需物品；
- 完成后的事件文案。

服务层只判断“当前动作是否满足该 stage 的完成条件”，不引用任何故事专名。

### 3. CLI 默认剧本

`scripts/agent-game.ts` 直接导入 `DARK_FANTASY_WORLD`。核心 API 已经支持任意 `World`，但 CLI 创建命令没有暴露内容文件入口。

未来应支持：

- `create --world-file <path>`；
- 或内容包/内容目录加载；
- 默认内容只作为 demo fallback，不进入核心服务。

### 4. demo 基础设施

`db/maintenance.ts` 固定 demo 用户和 seed 版本。这是开发/演示入口的约定，不是游戏领域层。它可以保留，但需要与“通用内容加载”区分：demo 基础数据不等于故事框架。

## 数据驱动目标模型

下一步优先建立内容层，而不是继续往 `apply` 加故事判断。

内容层至少需要表达：

- 世界宏观设定与规则；
- 场景、场景图、初始位置；
- 角色、属性、物品；
- 场景物品与角色物品；
- 武器 damage / block；
- 交互分支与完成条件；
- 状态语义与行为提示；当前沉睡类行为交由 profile / LLM，不进入系统规则；
- 内容版本与校验。

内容输入可以是 JSON、YAML 或 TypeScript seed，但最终必须经过统一校验后物化为数据库状态。数据库仍是运行时唯一真相，内容文件不是运行时状态源。

## 建议的优先级

P0：先把当前故事泄漏移出框架层。

- 通关条件改为 stage/world 内容字段；
- 完成事件改为通用文案或内容文案；
- 添加一个非灰烬墓园的最小内容 fixture，验证不改服务层即可运行。

P1：建立内容加载与选择。

- CLI 支持 `--world-file`；
- 内容 schema 校验；
- 内容版本与 `contentVersion` 绑定；
- 创建游戏时记录内容版本，便于回溯。

P2：内容包与工具链。

- 内容目录/包组织；
- 内容校验命令；
- 内容与测试夹具分离；
- 正式内容、临时测试内容、demo 内容的不同生命周期。

## 验收标准

未来完成数据驱动时，应满足：

- `src/game` 中不再出现具体故事名、钥匙名、鼠王、封骨之门等专名；
- 系统不匹配固定状态 key，也不内置特定故事的状态行为；
- 不需要修改服务层，就能用另一份 `World` 创建并推进另一段故事；
- CLI 能从内容文件创建游戏；
- 测试能用两个不同世界验证同一套规则；
- 临时测试剧本可以被替换或删除，不影响框架。

## 非目标

- 不把数据库改成内容文件数据库；
- 不让内容文件直接写运行时状态；
- 不把 LLM prompt 的全部文本硬编码进服务层；
- 不为每个故事写一套新的 apply 分支。
