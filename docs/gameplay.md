# 玩法数值

## 结论

玩法数值层拥有两件事：属性换算成结算值（攻击力、格挡、减伤），以及双方数值的对抗（查看与窃取的察觉与成败）。它是引擎里唯一能改「力量多算一点」「敏捷决定成败」「这条规则先关掉」的地方；动作流程只问结果，不问换算，拿到的攻击力与察觉与否都是这一层给出的定论。

这一层是纯函数：不读库、不调模型、不带随机。角色现值（本体属性加已穿戴物品）的聚合规则也在这里，`lookup` 只负责把物品行读齐；写回生命与观察仍归 `combat` 与动作本身。

现值只有一条口径：面板（`prompt` 的「你的状态」、`inspect_self`）与结算读同一份数字。生命上限是例外——装备的 `maxHp` 加成没有读取点，上限取角色自身的 `maxHp`。

源属性与终值的分层、以及 `damage` / `block` 为什么在角色身上只是顺时输出，归属性数据块 → 参见：[属性与终值](attributes.md)。

规则都有开关，集中在同一张表里。关掉一条时换算退化成最简形式，且面向 agent 的表述跟着同一份开关走——扣掉判定却留着描述，模型会按已经不存在的规则行动。

→ 参见：[数据驱动：边界与内容体系](data-driven.md)、[词缀](affixes.md)

## 临时的取舍

力量换算成伤害目前取 1:1，是开发期的临时曲线；格挡目前只来自装备，角色自身的源属性不产出防御；敏捷目前只决定查看与窃取的察觉与成败，没有第二个读取点；智慧没有读取点。替换时只动这一层与开关表，动作流程与内容写法不变。

## 设计口径

对方的敏捷对 agent 不公开，查看与窃取只能靠试。这是有意保留的信息不对称：把对方的数值摊开，对抗就退化成查表；提示词只给定性描述，不给数字。
