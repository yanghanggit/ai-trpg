# 外观（appearance）

外观是运行时动态量，不是身份。稳定视觉数据是签名上的 `form`，可见外观是 `appearances` 里的一条渲染记录：两者分层，换装只动后者。

## 模型

- `actor_signatures` 存稳定形态，一个 actor 同时只有一条在用的签名；换装不改写 `form`。
- `appearances` 是 append-only 渲染记录：每个签名只有一条当前记录，历史不覆盖、不删除。`ActorState.appearance` 只带展示文本与那条记录的 id，供追溯来源。
- `equipment` 是槽位到道具名的索引。道具不知道自己被谁穿着，穿戴状态只由 actor 维护。

## 签名

「可被看见的样子」是通用机制：换装追加记录；伪装、变身这类改变**身份可辨识性**的行为开一条新签名并封上旧的，于是认识旧签名的人看到新签名时认不出他。签名之间没有「本相 / 变体」语义，它们只是同一个 actor 的不同形态——面具、法术、诅咒由内容写成道具与设定。

actor 的 system prompt 用**开局签名**的 `form` 快照：跟着换装重写，会让「宪法」随每次换装漂移。

→ 参见：[术语表](glossary.md)

## 推理

外观是旁路的一层：旁路负责「借谁的记忆跑一轮推理」，外观只提供这一轮的生成、落账与骨架。业务决定选哪个任务、要不要广播；基建决定借谁的记忆、守卫怎么拦——输入由调用方给，守卫不跟着调用方走。`update` 的任务文本在本模块，`death` 在 `agents/death/corpse-appearance.ts`。

两个任务共用一把提交工具 `submit_appearance`：

- `update`：按 `form` 与参与外观的穿戴重新生成。不给旧外观，免得模型复述旧值。
- `death`：以刷新前的当前外观为底座，只叠加死亡带来的可见变化。状态词归引擎、材质词归内容的界线见[数据驱动目标](data-driven.md)。

两边共用的约束：

- 输入只到「角色自身」为止：不注入 stage 的 `environment` / `profile`，也不开放 `query`。外观是数据快照，追环境的实时变化没有稳定终点。
- 战役设定与全局规则由 actor 的宪法携带，任务输入不重复下发。
- 武器与护甲总是参与；饰品（`accessory`）由道具自己声明是否参与：项链看得见，植入物看不见，同一个槽位在不同题材里语义不同，引擎不替内容判断。声明同时决定被动可见性：不参与外观的饰品不进同舞台名单，换装也不给旁人任何信号；穿戴索引与 `inspect` 仍按索引走——藏着的东西要靠主动查看才翻得到。角色整体的隐匿（`concealed`）是另一层感知状态，不属于这个声明；见[信息披露](information-disclosure.md)。
- 提示词接在借来的记忆后面，所以一律用「你」称呼当事人；产出是第三人称、不带名字与引用的可见描述。
- 推理不写 memory，也不改 system prompt；失败不写记录，当前外观保持不变。

变化要不要写成事件由入口决定：`updateAppearance` 写，`rebuildAppearance` 与尸体刷新不写——维护性重推与死亡宣布各自已经说过同一个事实。广播与落账在同一个事务里。

## 来源快照

每条运行时外观都存下生成那一刻的完整输入，为的是复盘与必要时重放。`source` 只区分 seed 与 runtime。

## 换装入口

`equip` / `unequip` 在事务内只改索引；调用方提供外观服务时，提交后再补一次外观推理，失败只记日志、不回滚已落账的穿戴。只有涉及参与外观的道具的换装才重算并广播：输入没变，就不该写出一条「外观变了」。换装本身不写公共事件、舞台记忆与观察：发起人只收到自己的行动结果，旁人只看到外观变化；不参与外观的饰品因此完全无声。隐匿中的角色仍会写外观记录，但不广播；现身之后按最新记录呈现。

批量维护在 CLI，按生命状态分流；本模块只负责被点名的活人，尸体的刷新在 `agents/death/`。

→ 参见：[道具](items.md)、[数据库](database.md)、[Seed 内容编写原则](seed-authoring.md)

## 死亡

掉落与尸体外观同属旁路：都借死者自己的宪法，都不写记忆，差别只在产物落在哪张状态表。尸体外观以生前最后一条外观为底座写回同一签名，只跑一次——失败就保留那条记录，不补账、不重试。它不写外观变化事件：宣布阶段已经通知过全场与死者自己。掉落读的是此刻的可见外观，所以外观没跑成时读到的是生前那条。
