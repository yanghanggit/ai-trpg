# 外观（appearance）

外观是运行时动态量，不是身份。稳定视觉数据是签名上的 `form`，可见外观是 `appearances` 里的一条渲染记录：两者分层，换装只动后者。

## 模型

- `actor_signatures` 存稳定形态，一个 actor 同时只有一条在用的签名。`form` 统一写成 `种族:描述`，种族不加方括号——导出 Markdown 时方括号会被当成链接引用定义。换装不改写 `form`。
- `appearances` 是 append-only 渲染记录：每个签名只有一条当前记录，历史不覆盖、不删除。`ActorState.appearance` 只带展示文本与那条记录的 id，供追溯来源。
- `equipment` 是槽位到物品名的索引。物品不知道自己被谁穿着，穿戴状态只由 actor 维护。

## 签名

「可被看见的样子」是通用机制：换装追加记录；伪装、变身这类改变**身份可辨识性**的行为开一条新签名并封上旧的，于是认识旧签名的人看到新签名时认不出他。签名之间没有「本相 / 变体」语义，它们只是同一个 actor 的不同形态——面具、法术、诅咒这些说法由内容写在物品与设定里，引擎不为某个故事增加执行分支。

actor 的 system prompt 用**开局签名**的 `form` 快照：跟着换装重写，会让「宪法」随每次换装漂移。

→ 参见：[术语表](glossary.md)

## 推理

「借谁的记忆跑一轮推理」在 `src/game/agents/bypass/`：`target.ts` 装配目标（当事人、所在舞台、世界面名字表与它的记忆），`render.ts` 跑一轮并只认一个终止工具。外观是它的一层：分层在 `src/game/agents/appearance/`，`render.ts`（生成）、`record.ts`（落账 + 可选广播）是不带业务的基建；`compose.ts` 的 `runAppearanceTask` 是骨架，只调度「生成 → 落账」；`turn.ts` 只留活人两条业务入口。调用方控制的是选哪个任务、要不要广播，基建控制的是借谁的记忆、守卫怎么拦——输入由调用方给，守卫不跟着调用方走。任务文本归业务：`update` 在本模块，`death` 在 `agents/death/corpse-appearance.ts`，两边只共用提交工具、穿戴解析与可见性规则。

两个任务共用一把提交工具 `submit_appearance`：

- `update`：按 `form` 与槽位解析出的穿戴重新生成。不给旧外观，免得模型复述旧值。
- `death`：以刷新前的那份外观为底座（`base`），只给姿态、表面与结构三个维度。「死亡」「尸体」是跨题材通用的状态词，可以留在引擎；材质与痕迹的说法不点名——血还是漏液由形态与记忆决定。也不写穿戴掉落在哪、周围留下什么：那是引擎没有的机制，写进提示词等于教模型编造。

两边共用的约束：

- 输入只到「角色自身」为止：不注入 stage 的 `environment` / `profile`，也不开放 `query`。外观是数据快照，追环境的实时变化没有稳定终点——「淋湿」要再推导「换到干燥舞台后变干」，推不完。
- 战役设定与全局规则由 actor 的宪法携带，任务输入不重复下发。
- 饰品（`accessory`）不参与：这个大类的语义随题材漂移，引擎只保留槽位与穿戴索引，外观只消费武器与护甲。内容定义因此渗不进引擎。
- 提示词接在借来的记忆后面，所以一律用「你」称呼当事人；产出是第三人称、不带名字的可见描述，名字与引用由 `assertWorldFaceText` 拦下。
- 推理不写 memory，也不改 system prompt。
- 失败不写记录，当前外观保持不变。

外层看到的变化要不要写成事件，由入口决定：`updateAppearance` 写（自己一条用「你」，同舞台他人各一条用观察者相对的称呼或 `#编号`）；`rebuildAppearance` 不写——维护性重推的输入没变，不该产生事实；尸体的刷新也不写，它的通知已由死亡宣布覆盖。广播与落账在同一个事务里，不存在「外观变了但没人被通知」的中间态。

## 来源快照

每条运行时外观都存下生成那一刻的完整输入（prompt、任务文本、结构化摘要、底座），为的是复盘与必要时重放。`source` 只区分 seed 与 runtime；`context.task` 只是一个字符串标签，取值归业务，存储层不枚举任务。

## 换装入口

`equip` / `unequip` 在事务内只改索引；调用方提供外观服务时，`settleActorPlan` 在事务提交后补一次外观推理，失败只记日志、不回滚已落账的穿戴。于是换装是「规划 + 外观」两个 loop，玩家接管路径没有规划 loop，只有外观。

批量维护不在这里：`agent:game appearance --all` 在 CLI，读全表、按生命状态分流，活人逐个重推，尸体留给死亡阶段（那时才有尸体描写，且由收尾标记保证只写一次）。本模块只负责被点名的活人；尸体的刷新在 `agents/death/`。

→ 参见：[物品](items.md)、[数据库](database.md)

## 死亡

死亡阶段的编排与 `death` 任务文本都在 `agents/death/`；外观模块只提供生成、落账与骨架。掉落与尸体外观同属旁路：都借死者自己的宪法，都不写记忆，差别只在产物落在哪张状态表。收尾是逐人推进的：调用方先取待收尾名单，再对每个人调一次「宣布 → 尸体外观 → 掉落」，循环留在边界（行动落账、CLI）。尸体外观结果写回同一签名，只跑一次，推理失败就保留生前最后一条记录，不补账、不重试——宣布成功后这具尸体不会再被扫描到，开发期不为这一步引入新的待补状态。

于是三个阶段的重试语义不同，不要混为一谈：宣布是至少一次（认领失败就下次重试），尸体外观与掉落是至多一次。副作用是外观没跑成时，掉落读到的是生前最后一条外观，所以掉落任务只把它叫作「此刻的可见外观」，不向模型承诺那一定是尸体描写。

它不写外观变化事件：宣布阶段已经通知过全场与死者自己，再贴一条只是同一个事实说两遍。

## 种子数据

种子里的 `signature.appearance` 是预制结果，等于提前跑过一次推理：建局时成为该签名的第一条 seed 记录，运行时换装再追加。它遵循与运行时相同的输入规则（`form` + 非饰品穿戴 + 剧情痕迹）。

不写预制外观的 actor 回退到 `form`，也没有穿戴。
