# 后台作业队列（jobs）

本模块只提供后台作业基建：持久队列、worker、状态快照与等待；不包含 HTTP 路由、SSE 推送或具体业务作业。

## 命名

统一用 `job` / `jobId`：一行作业同时是概念与执行实例。`task` 留给 Node 与测试语境里的「异步任务」，本模块不用它。

## 选型

自建最小队列，不引入第三方队列运行时：队列表、串行键索引与归档都由本仓维护，迁移与 schema 的所有权只归 Drizzle。只继承外部队列的设计目标（持久、租约、重试），不继承其运行时与迁移机制。

→ 参见：[开发规范](conventions.md)

## 设计目标

长耗时工作不占 HTTP 请求：入口只入队并返回 `jobId`，worker 在请求生命周期之外消费。队列持久化在项目既有的 PostgreSQL，进程重启不丢；状态、最后一次错误与结果同行，不另设错误旁表。

## 性能位置

这类队列的容量最终都受 PostgreSQL 限制；pg-boss 不会突破数据库上限，只提供更完整的功能与运维手段。本项目的作业模型是长耗时 LLM pipeline，并发受串行键约束，数据库写入不是瓶颈。若未来出现大量短作业、多 worker 争抢或历史作业堆积，再评估 pg-boss / graphile-worker 或专用队列；届时优先调整索引、批量领取与归档，而不是先换库。

## 队列语义

`queue` 只用于 worker 分流；`serializationKey` 表达「同一房间 / 同一世界的 pipeline 不能并发」：同一 queue + key 的活跃作业最多一个，终态释放键。约束放在数据库唯一索引，而不是依赖调用方自觉。

worker 用租约与心跳处理进程失联，避免同一作业被两个 worker 同时执行；重试与不可重试由作业定义和 worker 共同决定。查询拿到的是快照，等待终态不依赖进程内事件，所以多 worker / 多进程看到同一份真相。

## 接入边界

HTTP 接入时只做两件事：入队并返回 `jobId`、把快照 / 等待暴露成路由；handler 永远不在路由请求里执行。业务作业在显式注册点登记，worker 不认识未注册的 kind，直接失败——不做目录扫描或隐式导入。

→ 参见：[架构与契约](architecture.md)

## 暂不包含

HTTP / SSE、作业取消、跨进程实时事件与具体业务作业都未实现；这些属于接入层或业务侧，不改变队列与 worker 的边界。
