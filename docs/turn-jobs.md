# 回合作业

回合作业是「一次回合」的执行载体：客户端入队，服务端在请求之外把这一回合跑完，客户端读作业的下场。

它是把回合从 HTTP 请求里拿出来的那一层。回合要调模型，耗时不确定，浏览器不该为一次推进挂住连接；作业还给了客户端一个可重新接上的把手——刷新、超时、换标签页，都能凭作业 id 回到同一个回合。

→ 参见：[后台作业队列](background-jobs.md)、[行动顺位](action-order.md)

## 范围

每个回合层一种作业：引擎跑循环的 NPC 回合、玩家直接提交动作的回合、舞台回合、world 回合。入队的粒度就是回合，一次入队只有一个；连着推几个是客户端串起来的事，不是一次批量。

空回合不占作业：它只给顺位加一，不跑循环。

## 与落账的关系

入队成功不代表回合发生过。计数与落账仍在服务层里完成，客户端只认作业终态。

结果里只放摘要：是否成功、事件游标、落了哪些动作。活状态与事件流由客户端重读——作业行不是第二份世界状态。

## 互斥与视图过期

同一局同时只允许一个回合在跑：后来的入队直接拒，不排队。串行键取局而不是角色，因为顺位上的回合本来就该一个接一个。这把锁记在库里，所以 API 与 worker 分进程、或多个 worker 并行时仍然成立。

视图过期在**执行开始时**比对，不在入队时：作业可能排队，入队那一刻的版本证明不了执行时还成立。

## 失败

不自动重试：落账不幂等，重跑一整回合可能留下重复副作用，重试归客户端。

失败码取错误对象自带的 `code` 原样留档——作业层不认识业务错误类型，客户端据此决定重读、跳过还是报错。

## 进度

回合跑起来以后会报阶段：NPC 回合是 `planning`（模型出计划）→ `applying`（落账）→ `finalizing`（读送达与游标）；玩家回合的计划是客户端给的，只有 `applying`；舞台与 world 回合只有 `planning`。

阶段写在作业行上，所以轮询与订阅看到的是同一份。「到第几轮了」这种细粒度不存在：一次入队就是一个回合，回合一多就是作业多。

## 查、撤、看

三条入口都在局这一层，作业只对本局可见：

- 列活跃作业——客户端重载后靠它接上「正在跑的那一个」，撞上「有回合在跑」时也靠它说清是谁。
- 按 `updatedSince` 列变更过的作业——断线重连补上错过的终态。
- 取消排队中的回合——只撤排队期；撤掉后串行键释放，可以立刻入队下一回合。
- 订阅作业状态（SSE）——先补发再转实时，每条事件是一份完整作业视图，`id` 就是下次重连的游标。

推送可能把同一作业的连续变更合并成一条：事件是快照，不是流水账。

## 谁在跑它

worker 由进程入口启动，用的是同一个作业注册表；把执行拆到独立进程只是换一个入口，注册表与串行键都不变。

## 暂不包含

执行中的取消、归档与清理都还没有；作业行暂时永久保留，开发早期回看比省空间重要。
