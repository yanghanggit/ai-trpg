# Actor 行动与记忆

## 第一级概念

`actor` 是第一级实体。NPC 与玩家不是两张表，而是同一个 actor 的两种控制者：NPC 由 agent loop 驱动，玩家通过接管关系直接提交行动。身份、场景归属、物品、状态与 memory 不因控制者改变；释放接管后，同一 actor 恢复 NPC 驱动并继续使用原 memory。

actor 只有一个运行时容器：`items` 道具队列。沉睡这类开局状态属于 `openingBriefing`，由 LLM 根据场景记忆判断何时解除，不是独立状态机。

## 两条入口，一个落库点

NPC 路径是环境观察 → agent loop → 计划与工具调用 → 提交计划 → 统一行动应用层；玩家路径直接提交行动，跳过计划与 LLM，同样进入统一应用层。差别只在行动如何产生；校验、版本递增、公共消息、目标与旁观者反馈、actor memory 写入共用同一套逻辑。

## 行动事实

记忆分三层，不能互相替代：actor 长期 memory 是下一次 LLM request 的稳定上下文；本次 loop 的完整消息（任务提示词、tool_calls 与结果）只进过程轨迹，用于审计与反查；`game_messages` 是公共事件流，供客户端增量拉取。长期 memory 不是公共消息，轨迹不是下一轮 prompt，公共消息也不承担私有记忆。

每次行动只落一条 action memory：做了什么、为什么、结果。可以有结构化元数据，但顶层长期记忆保持为一条可读事实，不保存逐轮对话。NPC 的「为什么」来自计划里的内心理由；玩家直接提交可以带理由，没有时明确标记为玩家直接提交。

长期 memory 由 system prompt、可选的 `openingBriefing` 与行动事实组成；compact 后 `[1..]` 收敛为一条 human summary。任务提示词、环境观察、工具调用与结果不单独成为长期记忆条目。

→ 参见：[开发期 Agent 工作流](debug-workflow.md)

## 过程轨迹

一次 loop 的全部消息——任务提示词、tool_calls 与工具结果、终止工具的提交——按回合写进过程轨迹，不进长期 memory。长期 memory 只留 system prompt、`openingBriefing`、观察与行动事实，因此下一轮 prompt 不会被上一轮的工具轨迹撑大。

轨迹不是状态：它不能决定角色知道什么，也没有「主动回读轨迹」的工具。

## 名字与指代

记忆本来就是按 actor 隔离的；缺的不是隔离，而是「什么时候允许把名字放进这段记忆」。名字不是地址，而是知识：`name_knowledge` 以「观察者 × 形象」为键，存的是这个观察者相信对方叫什么，可以是假名、误称或改口后的新名字。引擎不做名字抽取，写入只有两个入口：内容层的开局声明（`knownIdentities`，按 `Actor.key` 引用）和角色自己在回合里记下。

- **指代**：观察者看到的是 `@<形象序号>`，稳定、不透明、不含真名。工具参数、同场景名单与可作用对象都用它；台词里出现 `@` 数字会被解析层拒绝。
- **渲染**：名单写 `@3 奥德里克（此刻的样子）`，不知道名字时写 `@3 外观：…`；句子里的称呼只用名字或 `@N`，外观另起一行标注，不拼进句子。
- **写入**：`remember_identity` 只把「某个指代 → 我相信的名字」加入本轮计划，与动作同事务落账，不产生公共事件、不占行动名额；只有认知更新的计划也是合法回合。
- **形象切换**：名字按形象存，所以伪装 / 变身换成新形象后，认识旧形象的人认不出；切回旧形象时旧名字立刻恢复，不需要重新认识。
- **可见边界**：`look_stage` 只允许本场景。`game_messages`、stage / world 的观察与报告仍是上帝视角（客户端就是上帝），但 stage / world 写出的 environment、世界裁决与结局文案会经过统一守卫，禁止角色本名、`@N` 与类别前缀；actor 读取 environment 时还会再按观察者渲染一次。
- **观看者投影**：客户端要按角色视角展示时，读该 actor 的记忆与场景指代（`getActorView`），不要重新渲染公共事件流——事件文本在写入时就已经带规范名。玩家接管期间也能替角色记录称呼（`playerRememberIdentity`），否则交回 NPC 后它会“不知道自己听过名字”。投影里的自己的名字、场景名与出口都已去掉类型前缀，客户端可直接显示。
- **可选告警**：记名字时若对方不在场（`unseen_handle`），或这个称呼撞上同一观察者的旧信念、别人的本名（`name_collision`），只写轨迹与日志，不阻断行动。
- **玩家对话审核**：玩家接管的 `say` / `whisper` / `announce` 在写库前经过无状态审核；拒绝或审核不可用都会挡住动作，详见[玩家对话审核](dialogue-audit.md)。

## 开局简报

`openingBriefing` 是内容层给一个 actor 的本局私有简报（位于 `World.actors[]`，不是数据库字段），可含目标、任务、初始处境、约束与已知信息。它在建局时注入一次并进入长期 memory，因此后续仍能读到；不是单轮任务提示词，也不是公共消息。没有简报的 actor 不产生这条消息。

## 记忆压缩

actor、stage、world 的 memory 都遵循同一闭环：`[0]` 是 system，`[1]` 是 human，之后是运行历史。compact 把 `[1..]` 压成一条新的 human summary，memory 回到 system + summary；system 永远不动，不生成第二套状态。

摘要必须保留仍然有效的身份、目标、底线、关系、关键事实与未解决冲突。新 summary 归档被压缩的旧消息、条数与时间，也记录 `contextUsageRatio`；旧 summary 自身带更早的归档，所以连续 compact 形成可递归展开的树。

compact 只能手动触发：在事务外调用 LLM，在完整 turn 边界落账，LLM 失败或记忆在压缩期间变化时不改数据库。比例取自最近一条 AI 消息的 metadata，并在每次追加 AI 消息时写回。

## 任务提示词

任务提示词属于单次 loop 的临时输入，不进入长期 memory；它随轨迹保留，供事后还原当时的决策条件，下一轮重新生成。

## 工具

只读工具可多次调用、立即返回、不占动作额度：`look_stage` 看当前场景，`get_self` 返回自己的完整信息，`observe_actor` 只返回同场景目标携带的物品（含物品级数值与是否穿戴），不暴露对方的角色属性与生命。`query` 检索公共知识，参数是关键词而非整句提问。

→ 参见：[公共知识检索](rag.md)

动作工具彼此平级，每个工具的参数就是该动作的全部输入，没有中间分类或 `purpose` 参数，也不写游戏状态；是否一次返回多个调用由 LLM 决定，循环层按顺序串行执行。装配哪些动作工具取决于当前可用动作：角色固有动作，加上穿戴中物品提供的动作（例如装备了武器才有 `strike`）。`submit_plan` 是终止工具，只提交已暂存计划。

计划是有序动作列表，最多两条（`MAX_ACTIONS_PER_TURN`）；不做分类互斥，只限制条数。「通常一次沟通加一个其他动作」由提示词约定，超限时 handler 立即报错。两个动作按调用顺序应用，先移动后说话与先说话后移动结果不同。

每个成功应用的动作产生一条公共事件，`kind` 就是动作名，可见范围由动作决定（`whisper` 与 `steal` 为 private，其余为 stage）。同场景公开动作会向其他 actor 写入可见行动观察；`wait` 不改变场景状态。工具调用轨迹属于本次 loop，只进过程轨迹。

`hp` 为 0 的 actor 不能进入下一次 loop；伤害只写 `hp`，不判定死亡，收尾统一由死亡阶段完成，失败不进 actor 记忆。

## 沟通动作

| 动作 | 目标 | 听见范围 | 公共可见性 |
| --- | --- | --- | --- |
| `say` | 必须指定单个目标 | 发起者、目标、同场景其他 actor | stage |
| `whisper` | 必须指定单个目标 | 只有发起者与目标 | private |
| `announce` | 无目标 | 同场景所有 actor | stage |

`say` 的观察文本带双方身份，目标与旁观者都能读到；`whisper` 只有双方进入 memory；`announce` 按场景广播。受话者与旁观者不写「为什么」，只写发生了什么与当时的场景上下文；只有发起者写行动事实与理由。

## 移动与战斗的信息不对称

`move` 是唯一同时触及两个场景的动作，记忆刻意保持不对称：移动者本人知道从哪到哪；旧场景记忆只写「他离开了」，新场景记忆只写「他进入了」，两边其他 actor 各得到离开与进入观察。起点与终点的组合不写给任何旁观者，移动者也不会收到自己的离开 / 进入观察。

战斗按「谁的伤口」分流：只有受害者自己的反馈带剩余 HP；发起者与同场景旁观者只知道这一下造成多少伤害、对方是否倒下。完整数值只写进 `game_messages` 与舞台记忆。

文案由动作锁定：换视角只换人称，不换动作名——挥击即使带上武器也仍写作挥击，使用道具不会冒充挥击。

称呼遵守名字/指代分离：知道名字就写名字，不知道就只写 `@N`，外观单独一行写成 `@N 外观：…`。外观是辨认依据而不是称呼，不允许拼进句子（例如不能写成「对@15 肋骨从短毛下顶出来…肉搏」）。

## 物品与能力

动作分两种来源：角色固有动作写在 `actor.actions`；物品提供的动作写在 `item.actions`，只有该物品**穿戴中**时才借给角色。可用动作 = 固有 ∪ 穿戴中物品提供，顺序固定；工具列表、任务提示词里的动作列举、结算前的授权校验都用同一份结果（`allowedActionKinds`），不各自计算。

`strike` 是物品动作里目前唯一的一个：它由 `weapon` 槽的武器提供，武器必须显式声明 `actions: ["strike"]` 与 `damage` 效果，内容校验会拒绝其它组合。动作本身不带物品参数，武器隐式取 `equipment.weapon`；槽里没有武器、或武器不提供 `strike`，都直接报错，`strike` 没有空手分支。

身体攻击是另一个动作 `brawl`：它是角色固有动作，写在 `actor.actions` 里，不读任何物品，伤害只来自自身 `damage`，也不触发武器词缀。两者并存：有武器时可以挥击也可以肉搏，肉搏通常更弱，只作为武器被夺或未装备时的出路。文案各自锁定——`strike` 写「挥击（使用某武器）」，`brawl` 写「肉搏」。

装备变更不回灌解析期：`resolvePlan` 一次性解析完整份计划，装备快照取自回合开始，所以「本回合 `equip`，同回合 `strike`」不成立——先装备，下一回合才能挥击。这个限制是有意保留的，不为它把解析改成逐条应用。

`strike` 与 `use` 只是 dispatcher：选择物品、校验目标、调用 `item.effect`，具体效果由 `effect.type` 路由到的 handler 承担，每个动作最多引用一件物品。

- `damage`：固定公式 `max(0, 攻击方总 damage - 目标总 block)`，两侧都用 `addStats()`，目标装备在结算时现读；有 `affixes` 时默认效果跑完再补一次事务外 LLM 效果；补结算失败只丢增量，不回滚默认效果。追加伤害单独成句（词缀追加），并写进出手者记忆，不与默认效果混在一起。
- `event`：只写「使用了某物」的事件，后果交给 stage / world。

物品必须显式声明 effect，没有默认效果；`use` 的道具同样只按 `effect.type` 分派。新增 `heal`、`open` 等效果只注册新 handler，不在 `strike` / `use` 里写分支。

`equip` / `unequip` 只改穿戴索引：物品行不动，也不触发外观推理。

目标不需要存活：规则全局只有一条——行动者自己必须活着，尸体可以被说话、挥击、肉搏、给予、使用与偷窃。这是给复活类玩法留的口子，没有第二套过滤。

## 事务边界

LLM 与 agent loop 在数据库事务外完成。行动应用层在短事务中锁定 game、校验当前状态、应用变更、递增版本、写公共消息与 memory，不持锁等待模型返回。

同一 actor 的行动串行化；被玩家接管的 actor 由玩家入口提交，NPC 批量推进时跳过。

## 快照

开发期快照导出 actor 的 system prompt 与行动事实（在 memory 里）以及公共消息，供人工与 agent 观察；过程轨迹不进快照。快照是只读投影，不是状态源；正式环境不把私有 memory 暴露给客户端。
