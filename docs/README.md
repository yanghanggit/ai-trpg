# 引擎知识库

> `docs/` 只收引擎与系统，从这里出发定位任何引擎知识。使用说明与内容设定不在这里。

## 归属

文档分三层，一层一个所有者，不跨层复制：

- **引擎与系统** → `docs/`，由本页索引。
- **使用、启动与工具链** → 根 `README.md`。
- **内容与验收** → 与内容同目录的随附 md（如 `apps/server/seeds/dark-fantasy/bell-monastery.md`）。

## 写作约束（AI 编写文档时必须遵守）

总纲：**自述产物是唯一事实源**——代码、配置、生成物、`package.json` 的脚本、`.env.example`、seed。文档只写它们写不出来的部分。以下规则都是这条总纲的推论。

### 内容

1. **只写意图与关系。** 为什么这样设计、放弃了什么、系统之间怎么接、产物被谁消费。
2. **可失效性测试。** 问「自述产物一变，这句话会不会变成错的」。会，就不写——步骤、字段、默认值、命令、环境变量、工具参数、seed 内容都属此类，交给产物或测试。
3. **单一所有者。** 每条规则只在一个文档里写全，别处一律交叉引用指明所有者；两处说法不同时，先定所有者，再删另一处。
4. **删除测试。** 一段话删掉后设计意图仍然完整，就必须删；新增一段前，先找被它取代的那段话。文档的默认动作是删，不是加。
5. **符号只做锚点。** 领域类型名、文件名与命令可以直接引用；变量名、函数名、字段名只在需要定位时出现——把符号删掉，这句话仍要读得通。
6. **记录与结论分开。** 设计取舍、被否掉的方案及原因留下（避免重复踩坑）；运行日志、实测流水账、一次性数值不留，只留验收口径与当前结论。
7. **一篇一个系统。** 单系统的内部流程不写；系统之间的差异用交叉引用表达，不做同篇横比。
8. **只写引擎与接缝。** 客户端的呈现、交互与实现归属不写；跨层文档只写它与其他系统的关系，不写操作步骤。

### 形式

- 不用围栏代码块；命令、类型、文件名用行内代码。
- 交叉引用固定写作 `→ 参见：[文档标题](相对路径)`，放在段落末或独立行。
- 改名、删节或移动之前，先全仓搜引用（含代码注释里的 `docs/…`）。
- 先给结论，再给支撑它的关系；因果只交代必要的一层，比喻至多一句。

## 何时新建文档

- 出现一个独立的设计概念，其意图与关联无法用现有文档的一两段说清；否则更新已有文档。
- 临时或过渡内容必须在文档头写明生命周期与被替换的条件，并放在它所属的那一层。
- 新建、改名、合并或内容范围变化后，立即更新本页索引。
- 根 `README.md` 需要同时面向玩家与开发者时，把工具链与开发说明拆到 `DEVELOPING.md`，不让首页承担两套读者。
